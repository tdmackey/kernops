# Maintainer workflows

Step-by-step procedures. All patch work goes through `scripts/kpm`; this
document says which commands to run and where judgment is needed.

Conventions used below:

```sh
export WORK_ROOT=~/kernops        # must be Linux, on a case-sensitive filesystem
export KPM_LINE=7.3-lts           # the line you are working on (or --line <line>)
kpm() { ./scripts/kpm "$@"; }
```

Every `kpm` command accepts `--json` (put it before the command name).

## How the pieces fit

```
vendor trees ──harvest──▶ ledger ──import──▶ workbench branch ──export──▶ patches + series
                            ▲                     (work/<line>)                │
                  resolve, decide, policy                                      ▼
                                                                    apply ──▶ build tree
```

- The **ledger** (`kernel/lines/<line>/ledger/*.jsonl`) has one row per vendor
  commit with a decision: `carry`, `in-base`, `duplicate`, `dropped`,
  `deferred`, `superseded`, or routed as `config` / `packaging` / `noise`.
- The **series** and patch files are what gets built. They are generated from
  the workbench branch, never edited by hand.
- `kpm verify --strict` is the gate: every row decided, every carried row has a
  patch, the series applies to the base.

## Move a line to a new base

For 7.3-lts this is a new stable release; for the lines on an Ubuntu kernel, a new Canonical
publication. `kpm updates` reports both, for every line, along with vendor
sources that have moved past what the ledger last harvested; it exits 10 when
anything moved, and the daily workflow acts on the base rows automatically.

```sh
kpm fetch
kpm rebase v7.3.5
```

`rebase` marks carried patches whose content landed in the new base as
`in-base`, rebuilds the workbench on the new base, and re-exports the series.
It prints what dropped out and where it wrote the range-diff. Review both.

On a conflict it stops (exit code 3) and names the files:

```sh
cd <the worktree it printed>
# resolve to the upstream end state; see docs/backporting.md
git add <files>
kpm import --continue
kpm export
```

Then always:

```sh
kpm verify --strict
./scripts/build-line.sh 7.3-lts resolute     # the config can change with the base
```

A resolved patch is marked `adapted` in the ledger. Add a `Conflicts:` note to
its commit message saying what you changed and why; the next person to rebase
it will need that.

## A vendor published a new tree

```sh
kpm fetch
kpm harvest              # new, vanished and re-identified commits per source
kpm resolve              # in-base, duplicates, exact revert pairs, policy
kpm status
```

- **New** commits become `carry` if `policy.toml` says so, otherwise stay
  `undecided` for you to triage with `kpm decide`.
- **Vanished** commits are listed with their previous decision. The vendor
  dropped or rewrote them; decide whether we still want ours.
- Rows with a **proposal** (weak evidence, e.g. same subject) are never applied
  automatically. Check the diff, then `kpm decide`.

Then `kpm import && kpm export && kpm verify --strict`, and rebuild. If the
vendor changed its config, run `kpm config --write` and review the diff of
`config/union.json`.

## Carry one of our own patches

```sh
kpm fetch mainline
kpm add <sha> [<sha>...]       # skips anything already in the base
kpm import && kpm export
kpm verify --strict --fixes mainline/master
```

`--fixes` fails if upstream has a `Fixes:` follow-up to something we carry
that we do not have. Add those too.

Our patches live in the `6000-local` band. Take the minimal prerequisite
chain, in upstream order; see [backporting.md](backporting.md).

## Decide what happens to a vendor patch

```sh
kpm why "<sha | C-00123 | subject text>"
kpm decide dropped  C-00123 --reason "..."
kpm decide deferred C-00456 --reason "needs forward-port from 7.0"
kpm decide carry    --source azure --subject 'hyper-v'
kpm import && kpm export
```

`dropped` and `deferred` require a reason. A selector (`--source`,
`--subject`) only touches undecided rows unless you pass `--force`.

Standing rules go in `kernel/lines/<line>/policy.toml`, not in repeated
`decide` commands.

## Change the kernel config

Config for the stable lines is layered:

1. Ubuntu master's annotations (from the pinned Ubuntu tag).
2. `config/union.json`: options a vendor turns up. Generated by
   `kpm config --write`; do not edit.
3. `config/local.toml`: our own decisions, each with a note. Edit this.

The union only turns options up, so any Kconfig **choice group** where vendors
disagree must be settled in `local.toml` by naming every member.

After a change, `./scripts/build-line.sh <line> <series>` re-renders the
packaging and stops if the config does not settle, listing the options whose
requested value did not hold.

## Build

Build each series in its container. Make the container image one time:

```sh
podman build -t localhost/kernel-builder:noble -f env/Containerfile.noble env/
```

Then build:

```sh
./scripts/in-builder.sh noble ./scripts/build-line.sh 7.3-lts noble      # kernel, modules, headers, tools
./scripts/in-builder.sh noble ./scripts/build-line.sh 7.3-lts noble binary-headers binary-kernops   # no tools
RELEASE=1 ./scripts/in-builder.sh noble ./scripts/build-line.sh 7.3-lts noble   # debug symbols, ABI checks
SERIES=noble ./scripts/vng-boot.sh 7.3-lts                               # boot the result in a VM
```

On a machine that runs the target series, you can run `build-line.sh` without
the container.

`build-line.sh` has five stages:

1. Make the source tree from the base and the patch series.
2. Write the packaging for the series.
3. Settle the kernel config for the compiler of the series.
4. Build the packages.
5. Record what was built. `SBOM=0` skips the bill of materials.

The output is in `$WORK_ROOT/build/<line>/<series>/`:

| File | Contents |
|---|---|
| `*.deb` | The packages. |
| `linux-<vendor>_<version>_<arch>.buildinfo` | Each package that was installed for the build, with its version. |
| `sbom/<flavour>/sbom-source.spdx.json` | The source files that the build compiled, with hash and licence. |
| `sbom/<flavour>/sbom-output.spdx.json` | The kernel image and each module. |
| `sbom/<flavour>/sbom-build.spdx.json.zst` | Each intermediate file and the command that made it. |
| `sbom/<flavour>/patches.json` | For each patch of the patch series: whether it changes a file that this build compiled. |

The SBOM comes from the kernel's own tool (`scripts/sbom` in the kernel tree,
`Documentation/tools/sbom`). It does not include `perf`, `bpftool` and the
other tools.

`7.0` builds the same way, for each series:

```sh
./scripts/in-builder.sh noble    ./scripts/build-line.sh 7.0 noble
./scripts/in-builder.sh resolute ./scripts/build-line.sh 7.0 resolute
```

Its base is an Ubuntu kernel, not an upstream stable release. `kpm packaging`
renders our packaging from the `debian.master` of that base, and `kpm config`
merges the config of the vendors' 7.0 kernels. The kernel has no `scripts/sbom`
in 7.0, so that build writes no SBOM.

`hwe-6.17` uses Canonical's packaging. It builds through
`scripts/build-all.sh hwe-6.17 "" noble <arch>`, which also builds the
out-of-tree modules and can publish.

## Userspace packages

Kernel-coupled userspace (pahole, makedumpfile, kexec-tools, crash, the BPF
tools, firmware) is rebuilt for each series from the version a newer Ubuntu
series ships. `userspace/matrix.tsv` pins what and from where;
`userspace/sources.lock` pins the checksum of each source.

```sh
./scripts/in-builder.sh noble ./scripts/build-userspace.sh noble                  # all noble rows
./scripts/in-builder.sh noble ./scripts/build-userspace.sh noble crash            # one package
```

For a series with no packages yet, build in this order:

1. `build-userspace.sh <series> dwarves`. The kernel build needs `pahole`.
2. `build-line.sh <line> <series>`. `bpfcc` and `bpftrace` need `bpftool` and
   the headers from this kernel build.
3. `build-userspace.sh <series>` for all rows.

Output goes to `$WORK_ROOT/userspace/<series>/`. On a machine that already is
the target series, `build-userspace.sh` can run directly if the build
dependencies are installed.

A package that needs more than a no-change rebuild gets a directory, composed
on top of Ubuntu's source in this order:

```
userspace/<pkg>/debian/                   packaging files that replace Ubuntu's
userspace/<pkg>/<series>/debian/          the same, one series only
userspace/<pkg>/patches/*.patch           source patches
userspace/<pkg>/<series>/patches/*.patch  the same, one series only
userspace/<pkg>/revision                  the number of our revision (default 1)
userspace/<pkg>/notes.md                  why it deviates, and when it can stop
```

Keep only the files that differ. Prefer a patch for `debian/control` to a
replacement of the file.

- To move a package to a new version: change the row in `matrix.tsv`, build one
  time, and commit the new line in `sources.lock`.
- To change our patches for the same version: increase the number in
  `revision`.

## Add a source tree

1. Add a stanza to `kernel/sources.toml` (band, URL, tag glob or branch, where
   its own commits start).
2. Add its name to `sources` in the line's `line.toml`.
3. `kpm fetch <name> && kpm harvest <name> && kpm resolve`.

Everything already carried from another source resolves by itself; the
remainder is what that tree has that we lack.

## Change the product name or architectures

Edit `kernel/identity.toml`. Package names, flavours, the patch branch prefix
and module package names follow. Patch files and ledgers do not contain the
name. After the first release a rename is a new package lineage.

## Update a module pin

1. Edit `modules/matrix.tsv` for the specific `line/arch/module` rows.
2. `./scripts/check-module-sources.sh <line> arm64 noble` (and `amd64`).
3. `PUBLISH=0 ./scripts/build-all.sh <line> "" noble arm64` (and `amd64`).

Module packages are versioned `<module-version>+kernel.<exact-kernel-version>`
and depend on that exact `linux-image` version. Do not relax that.

## Build and publish a release manually

```sh
RELEASE=1 ./scripts/build-all.sh <line> "" noble arm64
RELEASE=1 ./scripts/build-all.sh <line> "" noble amd64
./scripts/validate-apt-repo.sh $WORK_ROOT/repo noble
```

Add `PUBLISH=0` for a dry run. Each build writes `.publish-manifest` and
`provenance.json` under `build/out/<line>/<arch>/<run-id>/`. To tag:

```sh
./scripts/tag-release.sh <vendor>-<version> build/out/<line>
```

## Test that the packages install and work

```sh
./scripts/install-test.sh 7.3-lts noble
```

The test installs every package that we built for the series into a clean
system: the kernel, the out-of-tree modules, and all userspace packages.

1. **Install.** In a plain container of the series, all packages must install
   and configure. The test then checks the initramfs, the modules, the
   headers, and that each tool runs (`tests/install/smoke.tsv`).
2. **Boot.** The test boots the kernel in a VM and enters the installed system.
   It loads modules from the installed packages (also DOCA and NVIDIA), runs a
   BPF program, loads the kernel image with `kexec`, and reads the kernel log
   (`tests/install/in-vm.sh`).

| File | Purpose |
|---|---|
| `tests/install/smoke.tsv` | One command for each tool that must run. |
| `tests/install/exclude.tsv` | Packages that the test does not install, with the reason. |
| `tests/install/known-warnings.tsv` | Kernel warnings that the test accepts, with the reason. |

The result is in `build/<line>/<series>/install-test.json`.

The test does not cover the bootloader, the initramfs at boot, Secure Boot
firmware, or real hardware. `BOOT=0` skips the VM. `SIG_ENFORCE=1` boots with
module signatures enforced.

Run this test after each kernel build and after each change to a userspace
package. It found faults that the build did not: kernel packages that did not
install on noble, and a `kdump-tools` backport with a dependency that noble
does not have.

## Sign the kernel and the modules

A kernel module loads on a system with Secure Boot only if the kernel trusts
its signature. The kernel image starts only if the firmware trusts its
signature.

For a test, make a self-signed key. Do not use this key in production: the
private key is a file with no protection.

```sh
./scripts/make-test-keys.sh                       # writes $WORK_ROOT/keys/test/
K=$WORK_ROOT/keys/test

# 1. Build a kernel that trusts the certificate for module signatures.
TRUST_CERT=$K/signing.pem ./scripts/in-builder.sh noble ./scripts/build-line.sh 7.3-lts noble

# 2. Build the out-of-tree modules and sign them.
MODULE_SIGN_KEY=$K/signing.key MODULE_SIGN_CERT=$K/signing.pem \
    ./scripts/build-modules.sh 7.3-lts $WORK_ROOT/build/7.3-lts/noble noble amd64

# 3. Sign the kernel image. This writes the linux-image-<release> package.
./scripts/sign-kernel.sh 7.3-lts noble $K/signing.key $K/signing.pem

# 4. Install and boot with signatures enforced.
SIG_ENFORCE=1 ./scripts/install-test.sh 7.3-lts noble
```

What each part does:

| Part | How |
|---|---|
| Modules of the kernel | The build signs them with a key that it makes and then deletes. This is Ubuntu's method. |
| Out-of-tree modules | `build-modules.sh` signs them with our key. The kernel trusts the key because `TRUST_CERT` put the certificate in the kernel. |
| Kernel image | `sign-kernel.sh` signs it with `sbsign`. |

The build record names each extra certificate that a kernel trusts, so a
kernel that trusts a test key is visible on the status page.

Not done yet:

- A machine must have the certificate in its Secure Boot database, or enrolled
  as a Machine Owner Key, before it starts the signed image. The test does not
  check this: it has no UEFI firmware.
- The apt repository is not signed.
- Production keys. They must be in a hardware module or a signing service.
  `sign-kernel.sh` and `sign-module.sh` accept a `pkcs11:` URI for that.

## See the state of all lines

```sh
python3 tools/dashboard/generate.py -o ~/kernops/dashboard/index.html --json ~/kernops/dashboard/dashboard.json
```

The page has five parts:

1. **What needs action.** One row for each thing to do, with the command.
2. **Lines.** For each line: the base, the decisions for each source, the work
   that waits for something, and the open CVEs.
3. **Builds.** One row for each build record that `build-line.sh` wrote. The
   boot result comes from `vng-boot.sh`.
4. **Userspace packages.** Each row of `userspace/matrix.tsv`, and whether the
   package was built.
5. **Out-of-tree modules.**

The page reads the repository and `$WORK_ROOT`. It does not need a kernel
clone. `--offline` skips the questions to the network. The JSON file has the
same data, for scripts and agents.

## Find CVEs that a line does not fix

```sh
kpm cves --update                 # get or refresh the CVE records (about 600 MB)
kpm cves                          # the line's open CVEs
kpm cves --used-files ~/kernops/build/7.3-lts/noble/sbom/kernops/sbom.used-files.txt
```

The records come from the kernel CVE authority
(`git.kernel.org/pub/scm/linux/security/vulns.git`). For each kernel branch, a
record gives the commit that introduced the flaw and the commit that fixes it.

A CVE is **open** for a line when the record says that the kernel version is
affected, and neither the base nor a carried patch has the fix. The output
says what closes each one:

| Output | Meaning | What to do |
|---|---|---|
| fixed in vX.Y.Z | A newer release of the same stable series has the fix. | Move the line to that base. |
| backport | Only mainline or a different series has the fix. | `kpm add <commit>`, then `import` and `export`. |
| no fix yet | No branch has a fix. | Wait, or write a fix. |

With `--used-files`, the output also says if the build compiled an affected
file. A CVE in code that is not compiled does not affect that build.

### When a record is wrong for the line

A record can list a kernel as affected when it is not. This occurs when the fix
was written for older branches only, because upstream removed or changed the
code. The text of the record says so; its version data does not.

1. Read the record and the fix commit.
2. Make sure that the upstream commit that removed or changed the code is in
   the base of the line.
3. Add an entry to `kernel/lines/<line>/cves.toml`: `status = "not-affected"`,
   a `reason`, and that commit as `evidence`.

`kpm cves` then counts the CVE as examined. It accepts the entry only while
each evidence commit is in the base. It reports an entry that no longer
applies, and an entry for a CVE that the records no longer report as open.

Do not add an entry to hide a CVE that needs a backport.

Limits:

- For a line on an Ubuntu kernel (`7.0`, `hwe-6.17`), the check reads the history of the
  base for the upstream commits that it names. This needs the base in the
  unified repo (`kpm fetch`). A fix that Canonical wrote in a different way,
  without a reference to the upstream commit, shows as open.
- The check uses commit identity. It does not find a fix that a source applied
  with no reference to the upstream commit.

## Before opening or merging a PR

```sh
make check
kpm verify --strict          # for each line you touched
```

Do not merge a series change just because it applies. Review the range-diff,
the list of patches that dropped out, and anything marked `adapted`.

## Rules for AI agents

The same procedures apply. In addition:

- Use `--json` and act on exit codes (`3` = conflict, needs judgment).
- Never mark a row `dropped` or `deferred` without a specific reason, and
  never accept a proposal without reading both diffs.
- Never add `Signed-off-by`. Record what you changed in a `Conflicts:` note.
- A change is not done until `kpm verify --strict` passes and the build does.
